# SolomonPrime v0.3.2 Job Broker Security Boundary

## Corrected execution path

```text
Public API -> deterministic scheduler -> signed mesh endpoint
           -> unprivileged JobExecutor -> protected AF_UNIX socket
           -> root broker revalidation -> root-owned fixed runner
           -> transient systemd sandbox as solomonjob
```

The SolomonPrime API service retains `NoNewPrivileges=yes`. It never invokes
`sudo`, never receives a general privileged command channel, and cannot choose
an arbitrary executable for the broker.

## Broker checks

- AF_UNIX filesystem access is limited to the `solomonprime` group.
- `SO_PEERCRED` must match the configured SolomonPrime service UID or root.
- The workspace must be a direct, non-symlink `JOB-*` child of
  `/apps/solomonprime-jobs` and owned by the service UID.
- The manifest and source must be regular, non-symlink, non-world-writable
  files owned by the service UID.
- The broker recomputes and compares the manifest SHA-256.
- Only Python, Blender, and OpenSCAD fixed executors are accepted.
- Only `read_only` and `reversible` risks execute automatically.
- Runtime, memory, CPU, disk, and source-size bounds are independently checked.
- The runner itself must be root-owned and not group/world writable.

The broker has no network namespace, cannot read SolomonPrime secrets/state,
and can write only beneath the job workspace root. The child job gets a second
systemd sandbox, executes as `solomonjob:solomonprime`, and has networking
disabled unless the approved manifest explicitly enables it.

## Scheduler admission changes

- `locality_node_id` is now a hard constraint rather than a scoring bonus.
- Nodes above the workload's CPU saturation ceiling are rejected.
- Job admission requires available RAM at least equal to both `min_ram_gb` and
  the job's `max_memory_gb` limit.
- Common CPU, RAM, and GPU fields are normalized at the top level of `/v1/nodes`
  while the canonical `snapshot` remains intact.

## API discoverability

`POST /v1/jobs/submit` now uses explicit Pydantic request and response models,
so resource limits and accepted fields appear in OpenAPI and unknown fields are
rejected before scheduling.
